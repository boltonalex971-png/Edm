# Логистика — изменения для пользователей

Приложение «Логистика» (`/logistics`) охватывает справочники номенклатуры, тары, поставок, изделий, заказов, перепаковку, распределение, оператор-десктоп и дерево производственных процессов. Появилось в v1.13.0 и остаётся в фокусе большинства недавних работ.

## v2.0.0.0

- **Визуальное обновление v2 на основе общего пакета компонентов** (PR #58). Оболочка Логистики, разметка master/detail, выбор иерархии, поиск и табулированные таблицы связей теперь используют примитивы `@microprojects/edm-components`, поэтому токены, шрифты, плотность и цветовая схема согласованы с Технологиями, Консолью и новым Хабом. Главные экраны, оператор-десктоп, деревья настроек (Номенклатура, Типы тары, Процессы) и потоки изделий / заказов / распределения получили обновлённый вид; ввод использует унифицированные компоненты `Field` / `HierarchyPicker` / `RelationTable` вместо локальных копий плагина.
- **Add Item / Add Folder больше не падают с ошибкой «Failed to load data»**. Кнопки Add в master-дереве (и действие Add в пустом состоянии) раньше переходили на `/0`, который backend Логистики отвергал, потому что у него идентификаторы — Guid; маршрут нового элемента теперь использует пустой Guid как маркер, поэтому редактор открывается корректно для Номенклатур, Типов тары и Процессов.
- **Вкладки связей — добавление новой строки снова работает**. Кнопка «Add record» в таблицах связей (Номенклатура ↔ Типы тары, Сорта процесса / Спецификация / Подпроцессы, Спецификация заказа) раньше POST-ила новую строку с `id: 0`, которую Логистика отвергала, так как столбец id — Guid; теперь новые строки POST-ятся с пустым Guid, и backend создаёт их как новые записи.
- **Спецификация заказа — клик по строке компонента открывает панель распределения.** Клик по строке на вкладке «Спецификация» заказа раньше ничего не делал, потому что таблица передавала событие row-selected только через флажок, который не отображался; теперь срабатывает по обычному клику строки, и панель поиска / распределения изделий открывается справа, как раньше.
- **Новый заказ — автоинкрементный № заказа снова подставляется.** Панель «Создать новый» показывала пустое поле № заказа, хотя backend возвращал следующий по порядку номер; редактор захватывал значения формы на первом рендере (до завершения GET), и номер приходил позже. Форма теперь однократно ресинхронизирует поля из загруженных данных, поэтому номер — и любые другие значения по умолчанию из backend — подставляются как ожидается. То же исправление работает при переключении между элементами в master-дереве.
- **Поиск компонента — строки тары снова раскрываются.** Панель поиска (открывается из строки Спецификации заказа) использовала master-detail-раскрытие MUI X DataGrid — это функция версии Pro, которая в бесплатном пакете молча ничего не делает, поэтому колонка-«шеврон» была неактивна и содержимое тары не отображалось встроенно. Панель теперь использует раскрывающийся список на Box: «шеврон» слева переключает каждую тару; раскрытый вид показывает тот же TareSchematic; в режиме поиска клик по слоту выбирает изделия, а двойной клик по строке тары распределяет тару целиком (как до v2).
- **Спецификация заказа — переключатель «Скрыть полностью распределённые» теперь встроен.** Переключатель переехал в панель инструментов таблицы — поиск слева, переключатель справа — вместо отдельной строки над таблицей.
- **Вкладки заказа — Спецификация и Операции теперь только для просмотра.** На обеих вкладках показывались кнопка «Add record» в панели инструментов и действия Edit/Delete в строках, хотя соответствующие endpoint'ы их не принимают со стороны заказа. Теперь это чистые таблицы данных (строки Спецификации принадлежат спеке процесса; строки Операций создаются при Execute), без кнопки и без колонки действий.
- **Ссылка «Заказы» в шапке по умолчанию открывает «Активные».** Клик по «Заказы» раньше приводил на путь /orders без выбранной вкладки, и поиск молча уходил в режим Completed. Ссылка теперь перенаправляет на /orders/ongoing, поэтому Active виден по умолчанию.
- **Карточка и редактор заказа переорганизованы.** Карточка просмотра теперь показывает даты Start и Due и описание заказа рядом с существующими Amount, Номенклатурой и Процессом — больше не нужно переключаться в режим редактирования, чтобы прочитать расписание. В редакторе Amount вынесен из секции Identity и стоит рядом с выбором процесса, чтобы «что делать» и «сколько» заполнялись вместе; Identity сохраняет номер заказа и свободное описание.
- **Поиск заказов обновляется при удалении заказа.** У заказа, открытого из строки поиска, отсутствовал hint `type="order"`, поэтому Detail из пакета не отправлял инвалидацию сущностей при удалении и список поиска показывал удалённую строку до ручного обновления.
- **Спецификация заказа — у каждого заказа теперь свой снимок спеки процесса.** Раньше вкладка строила живой view, объединяя текущую спеку процесса с изделиями заказа, и навешивала всё более хитрые фильтры, чтобы скрыть строки, ставшие устаревшими из-за авто-форка версий. Это приводило к дубликатам после форка номенклатуры, ломало Start, когда изделия распределялись против устаревшей номенклатуры, и лишало архивированные заказы исторического представления. Каждый новый заказ теперь копирует активные строки спеки выбранного процесса в собственную таблицу при создании; последующие изменения процесса или его номенклатур на заказ не влияют. Строки спеки с удалёнными или завершёнными номенклатурами пропускаются при создании снимка, поэтому свежесозданный заказ несёт только актуальные компоненты. Заказы, созданные до этого изменения, стартуют с пустой вкладкой Спецификация — строки нужно добавить однократно.
- **Allocate / Repack — выбор по штрих-коду добавляет тару одним шагом** (PR #62). В Allocate Output и Repacking выбор тары по штрих-коду раньше оставлял её в picker'е до отдельного шага Add; выбор теперь сразу опускает тару в рабочую область (с автосозданием по типу тары по умолчанию для заказа, если штрих-кода ещё нет), так что сканирование идёт от ввода до заполненного целевого слота без лишнего клика.
- **Схема тары — клик по изделию открывает его карточку** (PR #63). Изделия в таре (на странице Items и внутри детали Тары) не были интерактивны; клик по изделию теперь открывает его в read-only sub-detail-панели рядом с тарой, чтобы можно было погрузиться в историю изделия, не покидая представления тары.
- **Sub-detail-панели закрываются после успешного удаления** (PR #66). Sub-detail-панели Тары и Изделия, открытые с родительского экрана, и встроенные detail-панели из таблиц связей раньше оставляли устаревший контент после удаления строки; панель теперь автоматически закрывается после успешного DELETE.
- **Master-дерево — drop на пустое место и обновление при удалении папки** (PR #70). Перетаскивание узла дерева на пустое пространство вне любой цели раньше молча ничего не делало; drop теперь делает fallback на видимый локальный корень, чтобы перемещение всегда приземлялось куда-то осмысленное. Удаление папки теперь также перезагружает дерево, чтобы папка исчезала сразу, а не висела до ручного обновления.
- **Подробные хлебные крошки во вложенных Detail-панелях** (PR #72). Каждая Detail (и каждая sub-detail из её строк) теперь показывает цепочку хлебных крошек к родительским записям, поэтому путь «Заказ → Тара → Изделие» виден в верхней части глубокой панели. Множественные ярлыки типов в цепочке также корректны (`Процессы`, `Типы тары`) вместо `Процессss`.
- **Деталь поставки — Компоненты теперь обычная вкладка связей** (PR #73). Панель Items в детали поставки была кастомной панелью с группировкой по таре и кнопкой «Add items» над ней; теперь это вкладка `Components`, построенная на том же `RelationTable`, что и Спецификация заказа и Сорта процесса — плоский список строк, поиск в панели инструментов, «Add items» справа — а клик по строке открывает карточку изделия в правой панели, как везде.
- **Генеалогия изделия — панель Inputs читается справа налево** (PR #74). Сторона Inputs в представлении генеалогии зеркалит свою разметку, чтобы текущее изделие было справа, а предки уходили влево, соответствуя естественному направлению чтения «откуда это?». Outputs по-прежнему текут слева направо от текущего изделия наружу.
- **Спецификация заказа — Required / Allocated отображаются как корректные числа.** Две числовые колонки печатали сырое double из backend, поэтому полностью распределённая подсчитываемая номенклатура могла отображаться как `0.9999999999999999` — значение математически верно (сумма дробных execution-link'ов, например 10 × 0.1 в IEEE 754), но воспринимается как баг. Обе колонки теперь проходят через общий хелпер `formatQuantity`: подсчитываемые номенклатуры округляются до целых, дробные обрезают epsilon-шум и хвостовые нули.

## v1.13.28

- **Перепаковка — Reset и видимость исходной тары** (`550d3bb`). Reset теперь корректно возвращает pending-перемещённые изделия в исходные слоты — перемещение клонирует изделия в целевую тару и оставляет исходные строки на месте, скрытыми из source-пула до Apply. Строка исходной тары остаётся видимой, пока все её изделия перемещены наружу, чтобы было видно, что вы убрали, и можно было вручную очистить тару, когда закончите.

## v1.13.27

- **Подвал с версиями и «Что нового»** (`c4d54f7`). В подвале оболочки Логистики теперь видны версия плагина, версия продукта EDM и ссылка «Что нового», открывающая страницу `/changes` с пользовательским журналом изменений (этот файл).
- **Унифицированное распределение и перепаковка** (`a466381`). Allocate-output, перепаковка и схема тары используют общий механизм выбора-и-перемещения с контекстным меню, легендами сортов и номенклатуры и одним фильтром видимости — выбор исходных изделий и сброс на целевую тару работают одинаково во всех трёх потоках.
- **Автоинкрементный номер заказа** (PR 28, PR 35). Новые заказы получают последовательный номер при сохранении (с сохранением формата предыдущего заказа — `1`, `2`, …, или формы с префиксом и ведущими нулями, например `ORD-0043`); деталь заказа показывает его как заголовок `#<номер>`, и он отображается в списке заказов десктопа, детали изделия и узлах дерева генеалогии. Заказы без положительного Amount отвергаются при сохранении с понятной ошибкой.
- **Доводка UX заказов** (PR 31, PR 32, PR 33, PR 34). Список заказов обновляется при создании или завершении заказа; после успешного Create правая панель переключается с формы New-Order на просмотр только что созданного заказа; целевой тип тары в allocate-output подставляется из значения по умолчанию для номенклатуры; панель деталей тары, открытая из вкладки заказа, использует предзагруженные изделия заказа, чтобы её цифра ёмкости соответствовала сводке строки (без двойного счёта split'ов распределения); пустая вкладка Output показывает «Ещё не выполнено» вместо пустоты.
- **Редизайн генеалогии изделия** (PR 30). Узлы дерева генеалогии показывают детали изделия при наведении, рёбра окрашены по происхождению (output, store, supply, split), а изделия, созданные напрямую без поставки или предка, помечены происхождением «store».
- **Жизненный цикл изделия: неизменяемое количество** (`8fd3ce9`). `Item.Quantity` фиксируется при создании и никогда не уменьшается — потребление отслеживается только через `ItemLink` — поэтому выполненные заказы сохраняют исходное распределение видимым в истории; расчёты заполнения тары и распределения заказа корректно учитывают частично потреблённые изделия, и шум счётчика изделий в уведомлениях устранён.
- **Даты в локальном формате** (PR 27). Поля дат и дат-времени в заказах, поставках, оператор-десктопе, деталях папки и таблицах связей рендерятся в формате вашей локали; UTC-метки времени из backend нормализуются перед разбором, поэтому больше не «дрейфуют» на ваш локальный сдвиг.
- **Корень по типу** (PR 26). Номенклатура, тип тары и каждый вид процесса (Manufacturing, Technology, Operation) открываются на собственном предварительно засеянном корне дерева каталогов, чтобы новая запись попадала под правильный корень автоматически.
- **Версионирование схем-сущностей с авто-форком** (PR 24, PR 37). При сохранении нетривиальной правки типа тары, номенклатуры или процесса, у которых уже есть живые или исторические ссылки, UI предлагает форк — правка становится новой версией, оригинал замораживается, а существующие изделия, заказы и история продолжают рендериться против той версии, при которой были созданы. Тривиальные правки (Имя, Описание) по-прежнему меняют сущность на месте. Picker'ы и master-дерево показывают только текущую версию каждой сущности, поэтому старые форки больше не появляются как дубликаты в списках выбора.
- **Кросс-пользовательское обновление и блокировки** (PR 19, PR 22, PR 23). Изменения, сделанные другим пользователем, распространяются в ваши открытые Master/Detail-вкладки через SignalR-канал Логистики; Copy и Delete в панели Detail отключаются (с tooltip'ом «Locked by …»), пока блокировкой владеет другой пользователь; кросс-сообщения о папках теперь корректно инвалидируют каждую leaf-type master-view, а не только ту, что соответствует типу самой папки.
- **Исправления master-дерева** (PR 20, PR 21). Целевые индексы drag-and-drop разрешаются относительно отрендеренного (отфильтрованного) дерева, а не сырых данных, чтобы drop попадал в нужную папку; per-tree-состояние корня живёт в per-instance React-контексте, поэтому навигация между видами процесса больше не сбрасывает новые элементы в папку предыдущего view.

## v1.13.22

- **Стартовые данные на пустой БД** (PR 4, PR 15). Setup сидит номенклатуру, типы тары и процессы по умолчанию, чтобы приложение было готово к работе из коробки; bundle EF теперь выполняет миграции Логистики наряду с остальным приложением, без ручного шага.
- **Фильтрация тары и происхождение «store»** (PR 11, PR 12, PR 14). Операторы видят только те типы тары и штрих-коды, которые допускает активная номенклатура и разрешают группы пользователя; изделия, созданные напрямую (без поставки, без выпускающего процесса и без link'а к родителю), помечены происхождением «store» в детали изделия и дереве генеалогии.
- **Качество picker'ов** (PR 10, PR 13). Все picker'ы каталогов используют иерархический drop-down tree, учитывающий политики групп пользователей; всплывающие окна расширяются до самой длинной записи, чтобы значения не обрезались.

## v1.13.0 — первый релиз

### Каталоги
- **Каталоги номенклатуры и тары** (PR 711, PR 712, PR 727, PR 734, PR 9). Полный CRUD по номенклатуре и типам тары с дробными количествами и единицами, отображаемыми встроенно, плюс двунаправленная связь между ними — редактируйте связь с любой стороны.
- **Пустые папки скрыты в picker'ах** (PR 826). Поддерживает читаемость дерева каталогов.

### Процессы и спецификации
- **Дерево процессов** (PR 708, PR 716, PR 824, PR 827, PR 828, PR 831, PR 833, PR 835, PR 836). Каталог производственных процессов с типом / родителем / конфигурацией; на каждый процесс вкладка спеки и сорта для технологических процессов; процессы представлены отдельными деревьями по виду со скрытыми корнями; picker родителя предлагает только разрешённые дочерние типы; в Settings по умолчанию открывается дерево Manufacturing; picker для нового заказа — drop-down tree, а не плоский список.
- **Исправления процессов** (PR 829, PR 834). Обработка вида процесса и фильтров групп каталогов работает согласованно.

### Поставки и изделия
- **Поставки и изделия** (PR 715, PR 724, PR 725, PR 733, PR 832, PR 840, PR 841, PR 842). Приёмка поставок и привязка их к процессу; Поставки и Изделия — отдельные страницы со своими фильтрами; изделия используют стандартную архитектуру master/detail; переключение между доступными и потреблёнными; полное дерево происхождения (генеалогии) для любого изделия; выходные изделия можно сортировать по сортам; разделение изделия работает с дробными количествами в спеке; create/update-правки надёжно сохраняются.

### Заказы, перепаковка, распределение
- **Заказы** (PR 720, PR 721, PR 722, PR 726, PR 731, PR 736, PR 843, PR 845). Просмотр и редактирование заказов с их строками и привязками процессов, выполнение операций, обслуживающих заказы, резервирование конкретных изделий, переключение между активными и завершёнными, ограничение формы нового заказа процессами типа «операция», сохранение правок, затрагивающих несколько процессов, и переорганизованная панель деталей со скалярными полями и табулированными таблицами связей.
- **Распределение** (PR 839, PR 846). Выбор изделий для распределения по строкам заказа в модальном окне, чтобы не терять контекст.
- **Перепаковка** (PR 3, PR 838, PR 849). Перемещение содержимого из одной тары в другую с порождением итоговых изделий; picker тары отражает то, что физически находится в таре, включая штрих-коды.

### Оператор-десктоп
- **Оператор-десктоп** (PR 7, PR 8, PR 735, PR 847). Однооконный UI для цеха, чтобы принимать, перепаковывать и завершать операции; изменяемые master/detail-панели; шаг Done закрывает активную задачу; алерты валидации появляются над формой, а не сдвигают её вниз.

### Авторизация
- **Схема авторизации и группы** (PR 758, PR 819, PR 823). Логистика использует новый платформенный поток входа с JWT-cookie identity; пользователи принадлежат нескольким группам, и права суммируются.

### Полировка и инфраструктура
- **Полировка** (PR 709, PR 710, PR 713, PR 714, PR 816). Начальные заглушки страниц и навигация с выравниванием иконок; ленивая загрузка сеток вместо пагинированных для длинных каталогов; универсальный backend для страниц каталогов; проект чисто запускается в dev и prod без per-developer-конфигурации.
